## 1. ข้อสรุป

**มีผลกระทบบางส่วน แต่ไม่จำเป็นต้องแก้ทุกโมดูล**

- รุ่นเริ่มต้นของ Matchday Hub ทำเฉพาะ 01 ได้: นัดถัดไป, ผลล่าสุด, เทียบ 5 นัด, สรุปด้วยกฎจากตัวเลข, ลิงก์ตรวจข้อมูล และบันทึกแมตช์เฉพาะเบราว์เซอร์ ใช้ API ฟุตบอลเดิมของ 02 → 07
- หากต้องการโลโก้ทุกทีมจากข้อมูลกลาง ต้องให้ 02 เปิด endpoint รายการทีมต่อจาก 07 ซึ่งมีข้อมูลนี้แล้ว
- หากต้องการชื่อสนามและจำนวนรอบทั้งหมดแบบมาจากข้อมูลฤดูกาล ต้องประสาน 07 และ 02 เพิ่ม field ตาม Contract
- หากต้องการบันทึกแมตช์แล้วเปิดได้ข้ามอุปกรณ์ ต้องเพิ่ม API/ตารางข้อมูลใน 02
- 03/04/05/06 **ไม่มีงานใหม่ที่บังคับสำหรับรุ่นเริ่มต้น** เพราะสรุปก่อนเกมใช้การคำนวณจากผลแข่ง ไม่ต้องเรียก AI
- เปลี่ยนชื่อ PANBALL/โลโก้แพนด้าและแยกทีมที่กำลังดูกับทีมโปรด ทำใน 01 ได้ โดยใช้ preferences API เดิม

ภาพออกแบบเป็นแนวคิด: สกอร์ วันที่ สนาม และสถิติในภาพไม่ใช่ข้อมูลสำหรับนำไป hardcode ในระบบ

## 2. ฟีเจอร์ที่ประเมิน

### ฟีเจอร์ใหม่ในภาพ PANBALL

1. เปลี่ยนแบรนด์เป็น PANBALL พร้อมโลโก้หัวแพนด้า
2. แทนกล่องแชทหลักบนหน้าแรกด้วย Matchday Hub — สรุปก่อนเชียร์
3. แสดงนัดถัดไปและผลล่าสุดของทีมที่กำลังดู
4. เทียบผล 5 นัดล่าสุดของสองทีม รวมชนะ/เสมอ/แพ้/ยิงได้/เสีย
5. สร้างประเด็นก่อนเกมจากข้อมูลที่ตรวจสอบได้ พร้อมเวลาข้อมูลและหลักฐาน
6. บันทึกแมตช์ที่สนใจ
7. ใช้แชทผ่านมาสคอสต่อ พร้อมเปิดประวัติและเริ่มแชทใหม่ได้

### ข้อกำหนดจากแบบก่อนหน้าที่ต้องรองรับร่วมกัน

- ตัวเลือกด้านบนมี 5 ทีมเดิม ใช้เลือกข้อมูล ไม่เปลี่ยนทีมโปรด ธีม หรือมาสคอส
- ทีมโปรดและธีมเปลี่ยนผ่านตั้งค่าส่วนตัวล่างซ้าย กดบันทึกจึงมีผล
- เพิ่มโลโก้ทุกทีมใน standings, League Snapshot และ fixtures
- ฟอร์มใช้ ✓ ชนะ / − เสมอ / × แพ้ และระบุนัดล่าสุด
- เปลี่ยนข้อความบนหน้าจอจากแมตช์วีคเป็นนัด และแสดงนัดที่ X จาก Y นัด

## 5. งานของ 01 — ทำได้ก่อน

### 01-A: แบรนด์และ state

- เปลี่ยนข้อความที่ผู้ใช้เห็น, logo, favicon, metadata, หน้า Login, AppShell และชื่อแชทเป็น PANBALL
- ไม่เปลี่ยนชื่อ service, database, cookie, Docker project หรือ API path เพียงเพราะเปลี่ยนแบรนด์
- เก็บ storage key เดิมไว้ได้; หากเปลี่ยนชื่อ key ให้มี migration เพื่อไม่ทำ preference/ตำแหน่งมาสคอสเดิมหาย
- แยก `browsingTeamId` สำหรับอ่านข้อมูล กับ `favoriteTeamId` สำหรับธีม/มาสคอส
- ปุ่ม 5 ทีมเปลี่ยน browsing เท่านั้น; ตั้งค่ามี draft, ยกเลิก และบันทึกผ่าน preferences API เดิม
- ยกเลิกการ PATCH ทีมโปรดอัตโนมัติใน flow ส่งข้อความ/เลือกดูข้อมูล
- เมื่อเปลี่ยนบัญชีให้ล้าง state/cache ที่ผูกบัญชี และป้องกัน response เก่าเขียนทับบัญชีใหม่
- สถิติ Admin ยังเป็นทั้งระบบ จนกว่า API จะมีตัวกรองทีมจริง ห้ามเปลี่ยนป้ายให้เหมือนกรองแล้ว

### 01-B: เลือกแมตช์และคำนวณฟอร์ม

- อ่าน season จาก status หรือฤดูกาลที่ผู้ใช้เลือก ส่ง `season` ชัดเจนทุกครั้ง
- นัดถัดไป: ทีมตรงกับ browsingTeamId, status SCHEDULED, kickoff ใช้งานได้และยังไม่ผ่านเวลา เรียงใกล้สุดก่อน
- LIVE แสดงสถานะแยก ไม่อ้างว่าอัปเดตสดแบบวินาทีหากระบบไม่มีข้อมูลเช่นนั้น
- ผลล่าสุด/ฟอร์ม: ใช้ FINISHED ที่มีสกอร์ทั้งสองฝั่งและเวลาใช้ได้เท่านั้น ตัดรายการซ้ำตาม match_id
- ฟอร์ม 5 นัด: เรียง kickoff จริง ไม่เรียง matchweek เพราะมีนัดตกค้าง; สำหรับสรุปก่อนเกมให้ใช้เฉพาะนัดก่อน cutoff ของเกมเป้าหมายและไม่เกินเวลาปัจจุบัน
- คำนวณ W/D/L และประตูจากมุมของทีม รวมสลับ home/away ให้ถูกต้อง
- ใช้ชุด matches เดียวกันคำนวณทั้งวงกลมฟอร์มและตัวเลขรวม; ไม่ใช้ยอดทั้งฤดูกาลจาก standings มาแทนยอด 5 นัด
- แสดงเก่า → ใหม่ และวงแหวนที่นัดล่าสุด พร้อมข้อความสำหรับ screen reader/คีย์บอร์ด ไม่สื่อด้วยสีอย่างเดียว
- หากมีข้อมูลเพียง N นัด ให้บอก “พบข้อมูล N นัด” ไม่เติมให้ครบ 5 หรืออ้างว่าข้อมูลครบเมื่อยังไม่ทราบ coverage
- รอบแรกจำกัดข้อมูลฤดูกาลที่เลือก ไม่ต่อข้ามฤดูกาลโดยไม่แจ้ง
- โหลดข้อมูลทีมคู่แข่งเท่าที่จำเป็น ใช้ cache/request deduplication ภายในหน้า; ยกเลิกหรือไม่รับผล request เก่าเมื่อเปลี่ยนทีม
- การเปิด Hub ต้องไม่สั่ง ingest หรือเรียกผู้ให้บริการฟุตบอลภายนอกจากเว็บ

### 01-C: สรุปก่อนเกมพร้อมหลักฐาน

- ใช้ template จากตัวเลข เช่น “อาร์เซนอลชนะ 3 จาก 5 นัดที่มีข้อมูล” ไม่เรียก chat/LLM ทุกครั้งที่เปิดหน้า
- แต่ละประเด็นเก็บรายการ match_id ที่ใช้คำนวณ และเปิดดูหลักฐาน/รายละเอียดเกมผ่าน route เดิมได้
- เวลาแสดงต้องมาจาก fetched_at ของข้อมูลที่ใช้; ถ้าหลายรายการเวลาไม่เท่ากัน ให้แสดงช่วงเวลา/รายรายการ หรือใช้เวลาที่เก่าสุดเป็นคำอธิบายความสดขั้นต่ำ
- fixtures.fetched_at ปัจจุบันมาจาก last_ingest_at กลาง ไม่ใช่การรับประกันว่าแต่ละ match สดเท่ากัน; ใช้ per-match fetched_at ประกอบ
- หากไม่มี timestamp ให้แสดง “ไม่ทราบเวลาอัปเดต” ไม่ใช้เวลาที่เปิดหน้าเว็บแทน
- ลิงก์หลักฐานเป็นหน้ารายละเอียดในเว็บได้ ไม่ต้องสร้าง doc_id ของ RAG หรือ URL ผู้ให้บริการขึ้นเอง
- ไม่สรุปเรื่องนักเตะบาดเจ็บ ตัวจริง ราคาต่อรอง หรือคำทำนาย หากไม่มีข้อมูลและฟีเจอร์รองรับ
- ถ้าข้อมูลไม่พอ แสดง empty/error state และ retry ไม่สร้างสถิติจำลองทดแทน

### 01-D: บันทึกแมตช์รุ่นเริ่มต้น

- เก็บ localStorage แยก user.id และ schema version; เก็บ match_id/season เป็นหลัก
- บอกใน UI ว่า “บันทึกในเบราว์เซอร์นี้” ไม่อ้างว่าซิงก์ข้ามอุปกรณ์
- เปิดรายการแล้วดึงรายละเอียดล่าสุด ไม่ยึด kickoff/status เก่าที่เคยบันทึก
- รองรับ storage ใช้ไม่ได้, JSON เสีย, logout/เปลี่ยนบัญชี, เกมถูกลบหรือ API 404
- ไม่ใช่ฟีเจอร์แจ้งเตือน ไม่เพิ่ม scheduler, push notification หรืออีเมลในรุ่นนี้

### 01-E: รักษาการเข้าถึงแชทเดิม

- เอา ChatPanel หลักออกจากหน้าแรก แต่เก็บความสามารถของ ChatPanel เดิมไว้ใน mascot/drawer
- ปุ่มมาสคอส, เปิดประวัติ, แชทใหม่ และคำถามตัวอย่างต้องเปิดแชทได้ทั้งหน้า `/` และหน้าอื่น
- ปรับเงื่อนไข openSignal ที่ยกเว้นหน้า `/`; ทดสอบร่วมกับ effect ปิดแชทเมื่อเปลี่ยน route
- ยังคง sources, feedback, loading, error, draft, session และ account isolation เดิม
- ถ้าผู้ใช้เลือกดู Arsenal แต่ทีมโปรด City ให้ข้อความที่ระบบเติมระบุ “Arsenal” ชัดเจน และให้ผู้ใช้เห็นก่อนส่ง
- รุ่นเริ่มต้นไม่ให้คำถามกำกวม เช่น “ทีมนี้แข่งเมื่อไร” อาศัย browsing team โดยลับ ๆ: แจ้งบริบทที่ใช้หรือขอชื่อทีม ไม่แก้ favorite เพื่อส่งบริบท

## 6. งานที่ต้องประสาน 02 และ 07

### DEP-01: โลโก้ทุกทีมจากข้อมูลกลาง — 02 จำเป็นสำหรับแนวทางนี้

**02 ทำ:**

1. เพิ่ม authenticated `GET /api/football/teams` → เรียก 07 `GET /football/teams` ผ่าน FootballDataClient
2. คืน `{teams: [...]}` ตาม Team object เดิม รวม crest_url, ไม่เปิด provider key ให้เว็บ
3. ส่ง X-Request-ID และ Problem JSON ตามมาตรฐานเดิม; test 200/401/upstream error
4. เพิ่มเส้นทางใน Contract §1 หลังได้ review จากผู้เกี่ยวข้อง

**07 ทำ:** ตรวจว่า teams ที่ ingest รวมทุกทีมในฤดูกาลที่ใช้งาน และ crest_url ใช้งานได้/เป็น null ได้ ไม่มีความจำเป็นต้องสร้าง endpoint teams ใหม่

**01 ทำ:** TeamCrest ใช้ team_id lookup; รองรับภาพโหลดไม่ได้, ขนาดคงที่, fallback และชื่อทีมอ่านได้; จำกัด URL/host ที่ยอมรับตามวิธีแสดงภาพที่เลือก ไม่ทำ URL proxy แบบเปิดรับทุกปลายทาง

**ทางเลือกไม่แก้ 02:** จัดโลโก้จริงเป็น assets ใน 01 map ตาม team_id แต่ต้องดูแลทีมเลื่อนชั้น/ฤดูกาลเอง ไม่ใช่ระบบโหลดโลโก้อัตโนมัติจากกลาง

### DEP-02: ชื่อสนามในภาพ — 07 เพิ่มข้อมูล, 02 ตรวจการส่งต่อ

- ข้อเสนอ field ใหม่ใน Match: `venue: {name: string} | null` แบบ optional; ชื่อ/schema นี้ยังไม่ใช่ Contract ปัจจุบัน
- 07 map จากแหล่งที่มี field จริง และบันทึกลง payload; ตรวจสิทธิ์แพ็กเกจ/availability ของ provider ก่อนรับปากว่าจะครบทุกเกม
- หากต้องใช้ detail ingestion เพิ่ม ต้องประเมิน quota และความถี่ก่อน ห้ามเพิ่ม API call ภายนอกทุกครั้งที่คนเปิดเว็บ
- 02 fixtures/match เป็น pass-through อยู่แล้ว ตรวจว่า field ไม่หลุดและเพิ่ม contract test
- 01 ใช้ venue ที่ได้รับ; null/missing แสดง “ยังไม่มีข้อมูลสนาม” หรือซ่อนบรรทัด
- ห้ามอนุมานสนามจากชื่อทีมเจ้าบ้าน เพราะบางนัดอาจย้ายสนามหรือสนามกลาง
- ไม่บล็อก Hub หากสนามยังไม่มีข้อมูล

### DEP-03: “นัดที่ X จาก Y นัด” — metadata ฤดูกาล

- แค่เปลี่ยนคำไทยเป็น “นัด” ทำที่ 01; ชื่อ API field `matchweek` คงเดิม
- ข้อเสนอเพิ่ม optional `total_matchweeks: number | null` ที่ 07 `/football/status` สำหรับ current_season
- 02 `/api/football/status` ต้องเพิ่ม field ใน response ที่เลือกส่งออกเอง มิฉะนั้น metadata จาก 07 จะไม่ถึงเว็บ
- หากรองรับฤดูกาลย้อนหลัง ต้องกำหนด metadata ผูกกับ season ที่ร้องขอ เช่น optional field ใน fixtures response ของ season นั้น; ห้ามนำ total ของ current_season ไปปะฤดูกาลอื่น
- 07 ต้องระบุที่มาของจำนวนรอบจาก metadata/config การแข่งขันที่ตรวจสอบแล้ว; จำนวนรอบไม่ใช่จำนวนเกมรวมทั้งลีก
- ห้ามหา Y จาก max(matchweek) ในข้อมูลที่โหลดมา เพราะอาจ ingest มาไม่ครบ
- 01 ถ้าไม่ทราบ Y ให้แสดง “นัดที่ X” ก่อน; 38 ในภาพเป็นตัวอย่าง ไม่ใช่เหตุผลให้ hardcode ทุกฤดูกาล
- ถ้ารุ่นเริ่มต้นใช้ config พรีเมียร์ลีกที่ยืนยันเฉพาะฤดูกาล ให้ระบุข้อจำกัดไว้ชัดเจนและไม่อ้างว่าอ่าน Y จาก API

### DEP-04: ยืนยันความครบของข้อมูลและลำดับฟอร์ม — 07 ร่วมตรวจ

- ให้ 07 ยืนยันขอบเขต fixtures ที่เก็บ (ฤดูกาลปัจจุบัน/ย้อนหลัง) และทดสอบผล FINISHED พร้อม score/kickoff รวมเกมเลื่อน/ตกค้าง
- current fixtures response ไม่มี flag รับรอง coverage: การได้ array ไม่ได้แปลว่าฐานข้อมูลครบฤดูกาล
- ถ้าต้องรับประกันคำว่า “5 นัดล่าสุดจริง” ให้ตกลง optional coverage metadata/กติกาข้อมูลครบก่อน; มิฉะนั้นใช้ “5 นัดล่าสุดที่มีข้อมูล”
- ถ้าตาราง standings ใช้ `form` ของ provider โดยตรง ต้องยืนยันลำดับและรูปแบบ comma/null ให้ชัด; Hub แนะนำคำนวณจาก matches เพื่อผูกหลักฐานรายนัดได้
- ไม่จำเป็นต้องเพิ่ม endpoint รวม Hub ในรุ่นแรก; พิจารณา aggregation/pagination เมื่อวัด payload/latency แล้วพบปัญหาจริง

## 7. ส่วนเสริมที่ต้องเลือกก่อน ไม่ใช่งานบังคับ

### OPT-01: Saved matches ข้ามอุปกรณ์ — เจ้าของหลัก 02

เส้นทางต่อไปนี้เป็น **ข้อเสนอใหม่ ยังไม่มีในระบบ**:

| Method/path ที่เสนอ | หน้าที่ |
| --- | --- |
| GET `/api/me/saved-matches` | รายการของผู้ใช้ปัจจุบัน พร้อม pagination ที่ตกลง |
| PUT `/api/me/saved-matches/{match_id}` | บันทึกซ้ำได้โดยไม่สร้างแถวซ้ำ |
| DELETE `/api/me/saved-matches/{match_id}` | ยกเลิกบันทึกแบบ idempotent |

- 02 เพิ่ม migration/table เช่น user_id, match_id, season, created_at และ unique(user_id, match_id)
- user_id มาจาก session เท่านั้น ไม่รับตัวเลือกเจ้าของจาก request
- Match เป็น UUID ของ 07 ไม่ใช่ provider ID; ตรวจการมีอยู่ผ่าน service ไม่สร้าง foreign key ข้ามฐานข้อมูลบริการ
- กำหนดกรณีแมตช์หาย/07 ไม่พร้อม, pagination, limit ต่อบัญชี และ error contract
- 01 เปลี่ยนจาก local bookmarks มา API; ย้ายข้อมูล local เฉพาะเมื่อระบุวิธี merge/deduplicate และบัญชีเจ้าของชัด
- 08 ทดสอบ migration/deploy; 07 ไม่ต้องเก็บ preference ของผู้ใช้

### OPT-02: AI เขียนบทวิเคราะห์ก่อนเกม

- ต้องให้ 02/03/06 ออกแบบเส้นทางและ schema แยก; 05 เกี่ยวข้องเมื่อใช้ retrieval ประกอบ
- `/report/weekly` เดิมเป็นรายงานสัปดาห์ ไม่ใช่ pre-match briefing และไม่ควรเปลี่ยนความหมายเพื่อใช้แทน
- ต้องกำหนด evidence, citations, freshness, timeout/cache, token cost, fallback และการไม่แต่งตัวเลข
- ถ้าจะแคช ต้องผูก match_id/ชุดข้อมูลหรือเวลา ingest และภาษา เพื่อไม่เสิร์ฟ briefing เก่าหลังเลื่อนเกม
- ไม่มีเหตุผลบังคับให้ 04 เพิ่ม classifier/model สำหรับหน้าสรุปแบบตัวเลข
- ไม่แนะนำในรุ่นแรก เพราะประเด็นที่แสดงในภาพคำนวณได้โดยตรงอยู่แล้ว

### OPT-03: ส่ง browsing context เข้าแชทโดยอัตโนมัติ

- ChatRequest ปัจจุบันมีเพียง session_id และ message; favorite_team_id มาจาก User
- หากต้องการให้คำถามกำกวมเข้าใจทีมที่กำลังดู ต้องตกลง optional browsing context ระหว่าง 01 → 02 → 03 พร้อมกฎ precedence และ test
- ลำดับที่แนะนำให้ทีมพิจารณา: ทีมที่ระบุในคำถาม > บริบทบทสนทนาที่ชัด > browsing context ที่แสดงให้ผู้ใช้เห็น > favorite fallback
- ไม่เปลี่ยนความหมาย favorite_team_id เดิม และไม่ส่ง team ใหม่ผ่านการ PATCH preferences เพื่อเลี่ยงการเพิ่ม Contract
- ทางเลือกที่ทำใน 01 ได้ก่อน: เติมคำถามที่มีชื่อทีมชัดเจนลง draft ให้ผู้ใช้ตรวจ/กดส่งเอง
