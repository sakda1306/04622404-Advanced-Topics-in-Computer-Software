# บทพูด Jev และผลการวัด — CareerMirror

สำหรับผู้รับผิดชอบบท 4 และบท 5 ของหน้า http://localhost:3000/present

อ้างอิงหน้าเว็บที่เปิดอ่านวันที่ 6 พฤศจิกายน 2026 และ docs/JevEvaluation.md ซึ่งรายงานผลวัดวันที่ 5 พฤศจิกายน 2026 ตัวเลขเป็นผลการทดลองที่บันทึกไว้ ไม่ใช่การวัดใหม่ในวันนี้ บทพูดหลักประมาณ 6–8 นาที ขึ้นกับความเร็วและการสาธิต

## 1. เข้าใจเรื่องทั้งหมดก่อนจำบทพูด

ลองนึกถึงระบบเป็นศูนย์บริการที่มีหลายแผนก ผู้ใช้เข้ามาถามเรื่องเงินเดือน ทักษะ หรือสายงาน เราต้องส่งคำถามไปยังแผนกที่ถูกก่อน คนที่เลือกแผนกนี้คือ **Router**

- **กฎ** เหมือนป้ายบอกทาง ถ้าถามว่า “เงินเดือน Data Analyst เท่าไร” ระบบเห็นคำว่าเงินเดือนและรู้ทางได้เลย
- **Jev** เหมือนเจ้าหน้าที่คัดแยกคำถามที่อ่านภาษายืดหยุ่นกว่าป้าย แล้วเลือกจากหมวดที่เรากำหนด
- **Groq ในงาน Router** เหมือนเจ้าหน้าที่สำรองที่รับช่วงเมื่อ Jev ไม่แน่ใจหรือเรียกไม่สำเร็จ
- **Groq ในงานเขียนคำตอบ** เป็นอีกหน้าที่หนึ่ง แม้ Jev เลือกหมวดได้แล้ว ระบบก็ยังใช้โมเดลผ่าน Groq เขียนคำอธิบายให้ผู้ใช้

ดังนั้น Jev ช่วยรับงานเลือกหมวด ไม่ได้รับงานเขียนคำตอบทั้งหมด และไม่ได้คำนวณคะแนนความเหมาะสมของผู้ใช้ คะแนนนั้นคำนวณด้วย Python

ข้อความไม่ได้ผ่าน Jev ทุกข้อความ กฎและด่านตรวจจัดการหลายข้อความได้ก่อน มีเพียงส่วนที่เหลือและต้องใช้โมเดลช่วยเลือกเส้นทางเท่านั้นที่ถึง Jev เมื่อเปิดใช้งาน

## 2. บทพูดพร้อมใช้ ตามลำดับหน้าเว็บ

ใช้ “ครับ” หรือ “ค่ะ” ตามที่ถนัด ข้อความในวงเล็บเหลี่ยมเป็นจังหวะเลื่อนหน้าหรือสาธิต ไม่ต้องอ่านออกเสียง

### บท 4 — เปิดเรื่องและอธิบายหน้าที่ Jev

[เปิดหัวข้อ Jev · เทคนิคใหม่ของโปรเจกต์]

“ต่อไปเป็นส่วนของ Jev ซึ่งเราเพิ่มเข้ามาเพื่อช่วยลดภาระของ Groq ครับ

ก่อนอื่น เวลาผู้ใช้ส่งข้อความมา ระบบต้องรู้ก่อนว่าเขากำลังถามเรื่องอะไร เช่น เรื่องเงินเดือน เรื่องทักษะ หรือการเลือกสายงาน ขั้นตอนเลือกหมวดนี้เราเรียกว่า Router

คำถามที่ตรงกับกฎชัดเจน ระบบตัดสินได้เองอยู่แล้ว แต่คำถามที่กฎตัดสินไม่ได้ เดิมต้องเรียกโมเดลผ่าน Groq มาช่วย

สิ่งที่เราเพิ่มคือให้ Jev ลองเลือกหมวดก่อน ถ้า Jev ตัดสินได้ ก็ไม่ต้องเรียก Groq ซ้ำในขั้นตอนเลือกหมวด แต่ถ้าไม่แน่ใจหรือเรียกไม่สำเร็จ เราก็ส่งต่อให้ Groq รับช่วงครับ

ส่วนการเขียนคำตอบภาษาไทยให้ผู้ใช้ยังใช้ Groq และการคำนวณคะแนนยังเป็นหน้าที่ของ Python เหมือนเดิมครับ”

### บท 4 — ประโยชน์และต้นทุน

[ชี้กล่อง $0.03 และตาราง Jev เทียบกับ Groq]

“เหตุผลที่เราต้องลดการเรียก Groq คือบัญชีมีโควตาจำกัด ทั้งจำนวนครั้งและจำนวน tokens ถ้าใช้โควตาไปกับการเลือกหมวดมาก ก็จะเหลือให้การทำงานส่วนอื่นน้อยลง

จากการทดสอบ Golden Dataset การเรียก Groq เฉพาะงานเลือกเส้นทางลดจาก 9 ครั้งเหลือ 3 ครั้ง เท่ากับลดไป 6 ครั้ง หรือประมาณสองในสามครับ

ตรงนี้ต้องแยกให้ชัดว่าเป็นการลดในงานเลือกเส้นทาง ไม่ใช่ลดการเรียก Groq ทั้งระบบสองในสาม

ต้นทุน Jev ที่ทีมคำนวณจากการทดลองอยู่ประมาณ 0.03 ดอลลาร์ ต่อการเลือกเส้นทางหนึ่งพันครั้ง ตัวเลขนี้เป็นค่า Jev เฉพาะส่วนนี้ ไม่ใช่ค่าใช้จ่ายทั้งหมดของระบบครับ”

[ถ้าจะสาธิตตัวเลื่อนค่าใช้จ่าย ให้ใช้เวลาไม่เกิน 20 วินาที]

“ตัวเลื่อนนี้เป็นการคำนวณตัวอย่างโดยใช้อัตราที่วัดได้ เมื่อมีข้อความมาถึงขั้นตอนนี้มากขึ้น ก็จะเห็นว่า Jev ช่วยแบ่งภาระไปได้เท่าไร แต่ผลจริงยังขึ้นกับลักษณะข้อความของผู้ใช้ครับ”

### บท 4 — ความแม่นยำและสิ่งที่ต้องแลก

[ชี้ตารางความแม่นยำและเวลา]

“สิ่งที่เราต้องตรวจควบคู่กันคือ ประหยัดแล้วคำถามยังถูกส่งไปหมวดที่ถูกต้องหรือไม่

ในชุด Golden ทั้งก่อนและหลังเพิ่ม Jev เลือกเส้นทางถูก 60 จาก 60 ครั้ง และในชุดใหม่อีก 43 ข้อ ทั้งสองแบบก็ถูกครบเหมือนกัน โดย Jev ตัดสินเองได้ 33 ข้อ

เราจึงพูดได้ว่า ในชุดที่ทดสอบ การใช้ Jev ร่วมกับ Groq ลดการเรียก Groq ได้ โดยไม่พบว่าความแม่นยำลดลง แต่ยังไม่มีหลักฐานว่าทำให้แม่นขึ้นครับ

สิ่งที่ต้องแลกคือเวลาเฉลี่ยเฉพาะชั้นที่ใช้โมเดลเลือกเส้นทาง เพิ่มจาก 257 เป็น 476 มิลลิวินาที หรือเพิ่มประมาณ 0.22 วินาที เพราะบางข้อความต้องถาม Jev แล้วไปถาม Groq ต่อ ตัวเลขนี้ไม่ใช่เวลารอคำตอบทั้งหมดของผู้ใช้ครับ”

### บท 4 — สาธิต Router

[ใช้กล่อง “ลองส่งข้อความผ่าน AI Router แล้วดูว่าใครตัดสิน” เลือกเพียง 3 ตัวอย่าง]

“ตัวอย่างแรก ถามเงินเดือน Data Analyst กฎจับหมวดได้เลย จึงไม่ต้องเรียกโมเดลมาเลือกเส้นทาง

ตัวอย่างที่สอง ถามว่าถ้าอยากเป็น AI Engineer ต้องเตรียมอะไรบ้าง ในตัวอย่างนี้กฎส่งต่อให้ Jev และ Jev เลือกหมวดได้ จึงไม่ต้องให้ Groq เลือกซ้ำ

ตัวอย่างสุดท้าย ถ้าข้อความกำกวมหรือ Jev ไม่ตอบ ระบบจะให้ Groq รับช่วงครับ

กล่องนี้เป็นภาพจำลองลำดับการทำงานเพื่ออธิบายแนวคิด ไม่ใช่การเรียก API สดเพื่อวัดผลใหม่ครับ”

### บท 4 — เหตุผลที่ใช้ Jev แค่จุดนี้

[ชี้กราฟ Jev ตัวเดียว และหัวข้อการทดลองที่ไม่นำมาใช้]

“เราไม่ได้ให้ Jev แทนทุกอย่าง เพราะเมื่อทดสอบให้เลือกเส้นทางโดยลำพัง Jev ถูก 55 จาก 62 ข้อ ส่วน Groq ถูก 61 ข้อ เราจึงเลือกให้ทำงานร่วมกัน

ทีมยังทดลองให้แทนกฎ ตรวจว่าประโยคมีหลักฐานรองรับไหม และเลือกเอกสาร แต่ผลยังไม่ดีพอหรือไม่เพิ่มประโยชน์ในวิธีค้นที่ระบบใช้อยู่ จึงยังไม่นำมาใช้ครับ

อีกประโยชน์หนึ่งคือ เมื่อ Jev เห็นต่างจากกฎ ทีมได้นำข้อความเหล่านั้นมาตรวจ แล้วพบจุดที่ควรแก้กฎ ในชุดตรวจเฉพาะกลุ่มที่แก้ ผลดีขึ้นจาก 3 เป็น 12 ข้อจาก 13 ข้อ แต่เป็นผลจากการแก้กฎ และชุดนี้เขียนหลังแก้ จึงยังใช้แทนผลจากผู้ใช้จริงไม่ได้ครับ

ตอนนี้ Jev ปิดไว้เป็นค่าเริ่มต้น ต้องเปิดตั้งค่าก่อนใช้งาน และยังต้องตรวจเกณฑ์ความมั่นใจกับข้อมูลเพิ่มครับ”

### บท 5 — วัดอะไรบ้าง

[เลื่อนหัวข้อ ผลการวัดและสิ่งที่จะทำต่อ]

“ส่วนผลการวัด เราแยกเป็นสามเรื่องครับ คือเลือกหมวดถูกไหม ค้นเจอเอกสารที่ถูกไหม และระบบส่วนต่าง ๆ ทำงานครบไหม

ชุด Golden มีทั้งหมดหนึ่งร้อยเคส แบ่งเป็นคำถามค้นเอกสาร 80 เคส และบทสนทนา 20 เคส โดยบทสนทนารันสามรอบ จึงเป็น 60 ครั้งที่เห็นในหน้าเว็บ ไม่ใช่คำถามคนละข้อทั้งหมด 60 ข้อ

งานเลือกเส้นทางถูกครบ 60 จาก 60 ครั้ง ส่วนชุดข้อความที่ถึงชั้นโมเดลอีกชุดหนึ่งถูก 43 จาก 43 ข้อครับ”

### บท 5 — อธิบายผลค้นเอกสาร

[ชี้กราฟ Hit@1 และ Hit@3]

“สำหรับการค้นเอกสาร เราเทียบการค้นด้วยคำสำคัญอย่างเดียว หรือ BM25 กับ Hybrid ที่ใช้ทั้งคำสำคัญและความหมายของข้อความ

Hit@1 หมายถึงเอกสารอันดับแรกถูกหรือไม่ ส่วน Hit@3 หมายถึงในสามอันดับแรกมีเอกสารที่ถูกอย่างน้อยหนึ่งชิ้นหรือไม่

จาก 80 คำถาม วิธี Hybrid พบเอกสารที่ถูกในสามอันดับแรก 79 คำถาม ส่วน BM25 พบ 71 คำถาม และถ้าดูเฉพาะอันดับแรก Hybrid ได้ 64 ส่วน BM25 ได้ 52 ครับ

ผลนี้สนับสนุนว่า Hybrid ค้นเอกสารได้ดีกว่าในชุดนี้ แต่การค้นเจอเอกสารยังไม่เท่ากับคำตอบสุดท้ายถูกครบทุกประเด็น เพราะระบบยังต้องนำเอกสารไปเขียนคำตอบต่อครับ”

### บท 5 — เทสต์และกรณีระบบล้ม

[ชี้ 78/78 และ 1,171]

“นอกจากนี้ ผลทดสอบ API ตั้งแต่รับคำขอจนตรวจผล ผ่าน 78 จาก 78 เคส และรายงาน unit test กับ integration test ระบุว่าผ่าน 1,171 รายการ

พูดง่าย ๆ คือ เราตรวจทั้งชิ้นส่วนย่อย ตรวจการเชื่อมกันของส่วนต่าง ๆ และตรวจการทำงานผ่าน API จริง แต่จำนวนเทสต์ที่ผ่านไม่ได้หมายความว่าจะไม่มีบั๊กเหลือเลยครับ

ถ้าเรียกโมเดลเขียนคำตอบไม่สำเร็จ ระบบมีการลองใหม่หนึ่งครั้ง จากนั้นใช้โมเดลสำรอง และถ้ายังทำไม่ได้ก็แจ้งผู้ใช้เป็นภาษาไทยพร้อมคืนโควตา เราจึงมีทางรับมือกับความล้มเหลว แต่อาจไม่ได้คำตอบสำเร็จทุกครั้งครับ”

### บท 5 — ข้อจำกัดและสิ่งที่จะทำต่อ

[ชี้กล่องข้อจำกัด และรายการงานถัดไป]

“ข้อจำกัดตอนนี้คือ ชุดทดสอบยังเล็กและทีมสร้างเอง ยังรอผู้ตรวจอิสระ และยังไม่ได้ทดลองกับผู้ใช้จริง เราจึงยังสรุปไม่ได้ว่าผู้ใช้จริงจะได้ผลดีเท่าตัวเลขนี้ครับ

งานที่จะทำต่อมีหกเรื่องครับ

หนึ่ง ทดลองกับผู้ใช้จริง เพื่อเจอคำถามที่ทีมอาจไม่ได้นึกถึง

สอง ให้ผู้ตรวจอิสระช่วยตรวจชุดคำถามและเฉลย

สาม วัดว่าระบบต้องตัดประโยคที่ตรวจไม่ผ่านออกบ่อยแค่ไหน เพื่อดูคุณภาพข้อความที่โมเดลสร้าง

สี่ วัดเวลาตอบทั้งกรณีทั่วไปและกรณีที่ช้า โดยใช้ p50 และ p95

ห้า เพิ่มการตรวจชื่อภาษาไทยในคำตอบ เพราะตัวตรวจชื่อปัจจุบันยังเน้นชื่อที่ใช้อักษรละติน

และหก แก้ปัญหาที่ผู้ใช้เปลี่ยนเรื่องแล้วระบบยังยึดหัวข้อเก่า เช่น เปลี่ยนจากถามเงินเดือนไปถามเรื่องทักษะ แต่ระบบยังเลือกหมวดเงินเดือนครับ

สิ่งที่เรายืนยันได้ตอนนี้คือ Jev ช่วยแบ่งภาระงานเลือกเส้นทาง ส่วนผลกับผู้ใช้จริงและคุณภาพคำอธิบาย ยังเป็นสิ่งที่ต้องวัดต่อครับ”

## 3. ศัพท์ที่ต้องเข้าใจจริง

| คำ | ความหมายง่าย ๆ | อย่าสับสนกับ |
|---|---|---|
| Jev | โมเดลของ TypeSafe ที่โปรเจกต์ใช้เลือกหมวดจากตัวเลือก | ผู้เขียนคำตอบทั้งหมด หรือผู้คำนวณคะแนน |
| Groq | ผู้ให้บริการที่ระบบเรียกใช้โมเดล ทั้งเลือกหมวดและเขียนคำตอบ | ชื่อโมเดลตัวเดียว |
| Router / route | ตัวคัดแยกคำถาม / หมวดที่ส่งคำถามไป | อุปกรณ์กระจายสัญญาณอินเทอร์เน็ต |
| Keyword rules | กฎที่คนเขียนให้จับคำหรือรูปแบบข้อความ | โมเดลที่เรียนรู้ความหมายเอง |
| Guard | ด่านตรวจข้อความ เช่น คำสั่งหลอกให้เปิดเผย system prompt | ตัวตรวจว่าคำตอบสุดท้ายดีทุกประเด็น |
| Fallback | ทางสำรอง เมื่อทางแรกใช้ไม่ได้หรือยังตัดสินไม่ได้ | การรับประกันว่าทุกคำขอสำเร็จ |
| Clarify | ขอข้อมูลเพิ่มหรือถามกลับ เพราะยังไม่ชัดเจน | การเลือกหมวดผิดเสมอไป |
| Tokens | หน่วยย่อยของข้อความที่โมเดลประมวลผล | จำนวนคำที่เท่ากันเสมอ หรือจำนวนผู้ใช้ |
| Golden Dataset | ชุดคำถามพร้อมคำตอบ/เกณฑ์คาดหวังสำหรับตรวจผล | มาตรฐานภายนอกที่รับรองระบบแล้ว |
| Hit@1 | มีเอกสารที่ยอมรับได้อยู่ที่อันดับหนึ่ง | คำตอบสุดท้ายถูก 100% |
| Hit@3 | ในสามอันดับแรกมีเอกสารที่ยอมรับได้อย่างน้อยหนึ่งชิ้น | ต้องถูกครบทั้งสามเอกสาร |
| Unit test | ตรวจชิ้นส่วนย่อย เช่น สูตรคำนวณ | การใช้งานจริงของผู้ใช้ทั้งระบบ |
| Integration test | ตรวจว่าส่วนต่าง ๆ ทำงานร่วมกันได้ | การตรวจฟังก์ชันตัวเดียว |
| API end-to-end | ส่งคำขอเข้า API จริงและตรวจผลตามสถานการณ์ | การคลิกหน้าเว็บครบทุกหน้าหรือรับรอง UX ทั้งหมด |
| parse_claims | โค้ดตรวจประโยคกับหลักฐานและเงื่อนไขที่กำหนดก่อนแสดง | ตัวพิสูจน์ความจริงทุกความหมายได้สมบูรณ์ |
| p50 | ค่ากลาง: ประมาณครึ่งหนึ่งของคำขอตอบได้ภายในเวลานี้ | เวลาเฉลี่ยเลขคณิต |
| p95 | ประมาณ 95% ของคำขอตอบได้ภายในเวลานี้ ช่วยเห็นกรณีช้า | เวลาช้าที่สุดของทุกคำขอ |

ตัวอย่าง p50/p95 เพื่อเข้าใจเท่านั้น ไม่ใช่ผลของโปรเจกต์: ถ้ามี 100 คำขอ และ p50 = 3 วินาที แปลว่าประมาณครึ่งหนึ่งใช้เวลาไม่เกิน 3 วินาที ถ้า p95 = 10 วินาที แปลว่าประมาณ 95 คำขอใช้เวลาไม่เกิน 10 วินาที ส่วนที่เหลืออาจช้ากว่านั้น

ทำไมยอมให้ช้าลง: ทีมกำลังแลกเวลารอเพิ่มบางส่วนกับการใช้โควตา Groq น้อยลง ยังต้องวัดเวลารอของคำขอทั้งหมดกับผู้ใช้จริงก่อนตัดสินว่าคุ้มแค่ไหน

## 6. โพยสั้นก่อนขึ้นพูด

1. ปัญหา: Groq มีโควตา งานเลือกหมวดก็กินโควตา
2. วิธี: กฎก่อน → Jev ในชั้นโมเดล → Groq เมื่อ Jev ตัดสินไม่ได้
3. ผลดี: Groq Router 9 → 3 ความแม่นยำในชุดที่วัดเท่าเดิม
4. สิ่งที่แลก: 257 → 476 ms และเพิ่มผู้ให้บริการที่รับข้อความ
5. หลักฐาน: Router 60/60, Hybrid Hit@3 79/80, API 78/78
6. ข้อจำกัด: ชุดทีมเขียนเอง ยังไม่ใช่ผลจากผู้ใช้จริง และยังไม่วัดคุณภาพคำตอบครบ
7. งานต่อ: ผู้ใช้จริง ผู้ตรวจอิสระ ตรวจประโยค เวลารอ ภาษาไทย และเปลี่ยนหัวข้อ

ถ้าจำตัวเลขรองไม่ได้ ให้ชี้ตารางแล้วอธิบายความหมาย อย่าเดาตัวเลข และให้พูดว่า “ในชุดที่ทดสอบ” เมื่อกล่าวถึงความแม่นยำ
