# Step 5.6 — Recommendation Flow Implementation Plan

**Goal:** `POST /v1/travel/recommendations` works end to end: the API validates and stores the request, a Celery worker calls the Travel AI Agent, the Safety Gate and sanitizer shape the result, progress is kept in Redis and streamed over SSE, and the client gets `200` (finished within P-02) or `202` + job.

**Architecture:** Router → application services → domain / infrastructure, as in `docs/04_project_structure.md` §2. The worker is the only caller of the Agent (D-03). The API commits the database rows, writes the initial job state to Redis, enqueues `run_recommendation(job_id)` and, in `auto`/`sync` mode, waits on the job's Redis event stream for up to P-02. The worker (`AgentRunService`) loads the job, calls `AgentClient` with progress callbacks, runs `assess()` (freshness R-07 → Safety Gate R-01..R-05 → sanitizer R-06), persists the result and publishes the final event. SSE reads the same Redis stream.

**Tech Stack:** FastAPI + Starlette `StreamingResponse` (SSE), SQLAlchemy 2 async + GeoAlchemy2, redis-py asyncio (HASH, STREAM, ZSET + Lua), Celery 5 (Redis broker), httpx, pytest + fakeredis + Testcontainers (PostGIS).

**Spec:** `docs/02_api_spec.md` §5.1–5.4, §6.1, §6.3, §9, §11.2, §13 · `docs/03_data_design.md` §3.2–3.8, §5.2 · `docs/04_project_structure.md` §3, §6.

## Global Constraints

- Python ≥ 3.12; layer rules of 04 §2 (`domain` stays framework-free — `tests/unit/domain/test_layering.py`; `services` do not import `app.api` or `app.schemas`; `api` uses `infrastructure` only in `deps.py`/`resources.py`).
- P-02 sync budget 8 s · P-04 job Agent timeout 60 s · P-05 job state TTL 24 h · P-21 retention 30 days · P-22 conversation retention 30 days · P-26 cache ≤ 300 s · P-27 bucket 15 min · P-32 recommend limit 10/min · P-33 active jobs 3 · P-34 streams 3 · P-35 heartbeat 15 s · P-45 context messages 10.
- Never answer `TRAVEL_NORMALLY` when weather/disaster data is missing or stale; HIGH risk always carries emergency instructions.
- The Celery message carries only `job_id` and `correlation_id` (no personal data).
- No token, email, question text or exact coordinates in logs or Redis key names.
- Git: the user commits and pushes; ask first. No AI attribution anywhere.
- Commands: `python -m uv run ...` (uv is not on PATH).

## Decisions made while planning

| ID | Decision | Why |
|---|---|---|
| D-37 | SSE is a hand-written `StreamingResponse` (replaces the `sse-starlette` proposal in D-23) | Starlette 1.6 already cancels the generator on disconnect; our own heartbeat also refreshes the stream slot (P-34); one dependency less |
| D-38 | The sync wait reads the job's Redis event stream (`XREAD BLOCK` ≤ 1 s per call); the `job:{id}:done` key is dropped | one mechanism for sync wait and SSE; blocking calls stay under the Redis socket timeout |
| D-39 | `jobs:active:{user_id}` and `streams:{user_id}` are ZSETs (member = id, score = expiry ms) updated by one Lua script | a crashed worker or dropped connection frees its slot on expiry instead of holding the whole set |
| D-40 | Stream tickets are stored under `sse:ticket:{sha256(ticket)}` and redeemed with `GETDEL` | the ticket is a bearer secret and must not appear in a key name |
| D-41 | Every recommendation belongs to a conversation: without `conversation_id` the backend creates one; the question is stored as a `user` message and the summary as an `assistant` message | the worker receives only `job_id`, and the question is stored only in `messages` (data design §3.5) |
| D-42 | One `agent_runs` row per `AgentClient.run()` call (`id` = `run_id`, `attempt` = job attempt); HTTP retries inside the call are only logged | retries reuse the same `run_id`, which is the primary key |
| D-43 | Minimal JIT user provisioning (`users` row per `iss`+`sub`) is added now; profile, consent and deletion stay in step 5.9 | recommendations need `user_id` |
| D-44 | `mode=sync` that does not finish within P-02 → `504 AGENT_TIMEOUT` (the job keeps running and appears in history) | the spec only defines `202` for `auto`/`async` |
| D-45 | The cache is only read in `auto`/`sync` mode; `async` always creates a job. A cached hit whose data became stale is treated as a miss | `async` clients expect `202` + job; freshness is re-checked at read time |
| D-46 | No Celery-level task retry: `AgentClient` already retries (P-07); anything else marks the job `failed` | keeps one retry policy |
| D-47 | Output `service_status` only lists known services (`weather`, `transport`, `disaster`, `risk_model`, `rag`, `llm`); the gate still sees every reported service | R-06: no internal service names reach users, but degradation still counts |
| D-48 | When R-02 removes `TRAVEL_NORMALLY`, the Agent's `reasons` and `suggested_departure_time` are removed too | they argue for the removed action |
| D-49 | Progress messages are generated by the backend per language; the Agent's progress text is ignored | untrusted text, wrong language |
| D-50 | Celery tasks run on one `asyncio.Runner` per worker process (refines D-20) | DB/Redis/httpx pools are bound to one event loop and can be reused |
| D-51 | Keep redis-py 6.4, the newest version `kombu[redis]` accepts (`<6.5`) | added during execution: installing Celery downgraded redis-py from 8.1 |

New tunables: **P-53** `SSE_MAX_STREAM_SECONDS` = 300 (the client reconnects with `Last-Event-ID`), **P-54** `STREAM_TICKET_SECONDS` = 60 (D-06).

Deferred: `GET /v1/travel/recommendations` list (E-02) → 5.7 with cursor pagination; `DELETE /v1/jobs/{id}` (E-05) and the reaper → 5.9; `prediction_records` → 5.9 (needs analytics consent); `beat` container → 5.9 (no schedule yet); forwarding `place_id` of origin/destination (no column) → open question.

### Task 5: Worker use case `AgentRunService`

**Files:**
- Create: `app/services/agent_run_service.py`
- Test: `tests/integration/test_agent_run_service.py`

**Interfaces:**
- `AgentRunService(repository, agent: AgentPort, job_state, slots, cache, settings: Settings, clock: Clock)`
- `async run(job_id: UUID) -> JobStatus | None` (`None` = nothing to do)

**Flow:** `start_job` → `None` returns. Update Redis (`running`, `fetching_data`, 20) and publish `progress`. Build `AgentRunRequest` (`run_id = new_id()`, intent `FOLLOW_UP` when context exists else `CHECK_SAFETY`, pseudonymous profile, `deadline = now + P-04`, `max_tool_calls`). `on_progress` maps the Agent stage to our % and localized message (D-49) and publishes. Success → emergency fallback (region of destination, else origin; language, else `en`) → `assess` → `finish_job(succeeded)` → cache put if `cache_key` and `result_is_cacheable` → Redis `succeeded/completed/100` → publish `completed {job_id, status, result_url}`. `SafetyGateRejection` → code `DEPENDENCY_UNAVAILABLE` when `agent_failed` else `AGENT_BAD_RESPONSE`; `needs_safety_review` logs `safety_review_required` (rule, run_id). `AgentCallError` → `to_app_error().code`. Any other exception → `INTERNAL_ERROR` (logged with type only). Bugs found by running the Docker stack (each got a failing test first):

1. Worker child processes printed no logs: Celery redirects their stdout into logging, which loops back to stdout. Fixed with `worker_redirect_stdouts=False`.
2. Every job reused the first job's `correlation_id`: `asyncio.Runner.run()` uses the runner's saved context. Fixed by passing `contextvars.copy_context()` (`tests/unit/test_workers.py::test_runtime_runs_each_job_in_the_callers_context`).
3. A client that disconnected kept its stream slot until the 45 s TTL: Starlette cancels the stream task, and the `finally` cleanup was cancelled too. Fixed by polling `request.is_disconnected` inside the stream loop and shielding the release (`anyio.CancelScope(shield=True)`); `test_stream_slot_is_released_when_the_response_is_cancelled` fails without the shield. Verified live: the slot is gone right after `curl --max-time 3` ends.
